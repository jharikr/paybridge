# Paybridge simulated payment proof of concept

Implementation completed on 2026-10-11 in [draft PR #1](https://github.com/jharikr/paybridge/pull/1). All twelve tickets are complete. The original approval context and requirements below are retained; current execution evidence is in the [verification trace](../../docs/verification-trace.md).

## Problem Statement

Merchants in Anguilla that have their own NCBA/4Cs provider merchant keys need a hosted checkout experience without each merchant application implementing the provider integration and its payment-recovery behavior. Paybridge is intended to provide that service while keeping each merchant's payments and provider credentials separate.

Before building a customer-facing service, the owner needs a working proof of concept that demonstrates the complete payment journey with synthetic data. A successful payment alone is insufficient. The demonstration must establish what happens when a payment is declined, requests are duplicated or delayed, processes crash, notifications arrive out of order, or the financial outcome cannot be determined. It must also show how the merchant application records a payment safely and how an operator investigates an unknown outcome.

The repository currently contains project guidance and design documents. No application runtime, framework setup, database, package manifest, or application test suite exists.

## Solution

Build a local TypeScript reference implementation comprising Paybridge, a sample merchant application, and a durable mock 4Cs provider. Each application owns its persistence and communicates with the others over HTTP. Use the agreed stack and two seeded merchant contexts with separate synthetic provider accounts and credentials.

Demonstrate merchant payment creation and confirmation, the headless hosted-checkout protocol, browser-return navigation, durable provider work, signed webhooks, merchant receipt and processing, status lookup, and manual reconciliation. Exercise both normal outcomes and failures across real process restarts. The sample merchant application demonstrates the integration obligations that accompany the Paybridge API.

The proof of concept has no payer UI, onboarding portal, real card collection, live bank connectivity, or customer deployment. It establishes behavior under an explicit mock-provider contract and documents the live-provider questions that remain unverified.

## User Stories

Payer stories are demonstrated through headless checkout clients using synthetic payment-method references. They do not require a UI or real payments.

1. As a merchant, I want Paybridge to submit my payments under my own provider merchant account, so that another merchant's credentials cannot receive or determine my transactions.
2. As a merchant, I want my Paybridge API credential to be distinct from my provider merchant key, so that integrating applications do not confuse the two authorization boundaries.
3. As a merchant, I want every payment command and lookup scoped to my identity, so that another merchant cannot read or change my payments.
4. As a merchant, I want inactive or invalid API credentials rejected, so that disabled access cannot continue creating or changing payments.
5. As a merchant application developer, I want two seeded merchants with separate synthetic credentials and callback settings, so that I can demonstrate account isolation without building onboarding.
6. As a merchant application developer, I want each merchant to use its own business references, so that two merchants can use the same reference without their orders colliding.
7. As a merchant application developer, I want to bind an order to one payment intent and reuse it, so that interrupted checkout does not create another collectible payment for that order.
8. As a merchant application developer, I want to persist a command and its key before sending it, so that recovery after a lost response or restart repeats the same instruction.
9. As a merchant application developer, I want to create a payment with a fixed amount, currency, business reference, and return destination, so that its financial and business meaning remains stable.
10. As a merchant application developer, I want invalid amounts, currencies, URLs, headers, and unexpected fields rejected, so that malformed requests cannot become payment records.
11. As a merchant application developer, I want an identical creation command replay to return its original result, so that retrying a lost acknowledgment does not create another intent.
12. As a merchant application developer, I want reuse of a command key with different input or a different operation rejected, so that a key cannot silently identify two instructions.
13. As a merchant application developer, I want authenticated lookup of the current persisted payment state, so that I can recover without treating an old command acknowledgment as a current result.
14. As a payer, I want checkout access to require the capability issued for that payment, so that knowing a payment identifier alone does not authorize payment actions.
15. As a payer, I want checkout to expose the amount, currency, and current payment state, so that my confirmation is based on the payment being presented.
16. As a payer, I want a confirmation to be accepted only for the payment revision my checkout client received, so that a stale page cannot silently start another attempt after the state changes.
17. As a payer, I want a definite decline to permit a deliberate new attempt on the same intent, so that I can try again without losing the payment's history.
18. As a payer, I want an old delayed click rejected after an intervening decline, so that it does not become an unintended retry.
19. As a merchant application developer, I want an accepted confirmation replay to retain its original acknowledgment after the payment changes, so that recovery does not create a new attempt or misreport the command's identity.
20. As a payer, I want an uncertain outcome to block another financial attempt, so that a payment which may already have occurred is not repeated.
21. As a payer, I want leaving checkout to return me to the merchant without changing payment state, so that I can return to an otherwise payable intent later.
22. As a merchant, I want to cancel a pending intent explicitly before processing starts, so that I can permanently withdraw that payment request.
23. As a merchant application developer, I want the sample to retain an explicitly cancelled intent and its order binding, so that it cannot silently replace the cancelled request or erase its history.
24. As a merchant application developer, I want browser return to trigger verification rather than mark an order paid, so that navigation cannot be mistaken for payment evidence.
25. As a merchant application developer, I want return-route payment identifiers checked against the receiving merchant and local order, so that a substituted identifier cannot expose or update another merchant's payment.
26. As a merchant application developer, I want confirmation acknowledgment distinguished from financial completion, so that my application does not fulfill an order merely because processing was accepted.
27. As an operator, I want committed payment attempts to have durable provider work, so that a crash after command acceptance does not lose the payment instruction.
28. As an operator, I want recovery to reuse the original attempt, provider account, transaction identifier, and synthetic input, so that recovery does not become a fresh financial attempt.
29. As a maintainer, I want the mock provider to retain accepted transaction identity and final outcomes across restarts, so that duplicate recovery cannot produce another simulated financial effect.
30. As a maintainer, I want duplicate provider responses treated as evidence of prior identifier use rather than approval, so that previously declined or incomplete transactions are not reported as paid.
31. As a merchant, I want service-level and financial provider results interpreted separately, so that an HTTP success or service acknowledgment is not mistaken for financial approval.
32. As an operator, I want the provider's incomplete result distinguished from a bank decline, so that investigation retains the actual reported cause.
33. As a merchant, I want timeouts, malformed responses, mismatched identifiers, and other unproven outcomes classified as unknown, so that uncertainty does not authorize another attempt.
34. As a merchant, I want money converted without floating-point arithmetic, so that the amount submitted to the provider matches the amount requested.
35. As a maintainer, I want stable provider invoice and transaction references that satisfy the mock contract, so that arbitrary merchant references are not truncated into colliding provider identifiers.
36. As a maintainer, I want deterministic approval, decline, incomplete, timeout, lost-response, duplicate, and delay scenarios, so that failure demonstrations are reproducible.
37. As an operator, I want a committed unknown outcome to stop automatic financial submissions and create one reconciliation case, so that uncertainty is investigated through an explicit workflow.
38. As an operator, I want to list and start investigations of unknown attempts through trusted local commands, so that the prototype demonstrates operational recovery without an administration UI.
39. As an operator, I want to verify the actual outcome using evidence for the exact provider account and attempt, so that reconciliation can establish either success or definite non-payment.
40. As an operator, I want absent, mismatched, or inconclusive evidence to leave an investigation open, so that a missing record cannot be used to justify another payment while an old request may still execute.
41. As an operator, I want recorded resolution evidence, identity, time, reason, and outcome, so that another person can understand why the financial state changed.
42. As an operator, I want repeated identical resolutions to be harmless and conflicting resolutions rejected, so that concurrent or repeated commands do not rewrite an established result.
43. As an operator, I want a failed resolution to require an outcome that delayed same-ID submissions must still honor, so that allowing a fresh attempt does not leave an earlier request able to charge later.
44. As an operator, I want useful late provider observations retained even when a worker loses its claim, so that state protection does not discard evidence needed for investigation.
45. As a merchant, I want payment history preserved as facts and later events, so that retries, investigations, and operational failures do not erase what happened.
46. As a merchant application developer, I want signed webhooks verified against their exact bytes and the configured receiving merchant, so that untrusted or differently owned events cannot drive order state.
47. As a merchant application developer, I want to acknowledge a webhook only after durable receipt, so that a crash after acknowledgment does not lose the notification.
48. As a merchant application developer, I want duplicate webhook delivery to produce one receipt and one local paid effect, so that retries do not repeat business effects.
49. As a merchant application developer, I want newer payment revisions to supersede older snapshots regardless of delivery order, so that a delayed failure cannot undo a newer success.
50. As a merchant application developer, I want gaps in payment revision numbers accepted, so that notifications do not wait for states that have no webhook type.
51. As a merchant application developer, I want webhook processing and lookup fallback to share ownership and revision rules, so that their race cannot regress local state or repeat the paid effect.
52. As a merchant application developer, I want receipts with temporarily missing local bindings retained for recovery, so that an early webhook is not discarded before its order association is available.
53. As a merchant application developer, I want orders, prepared commands, payment bindings, and inbox receipts to retain merchant context, so that one merchant's valid callback cannot update another merchant's order.
54. As a merchant, I want webhook delivery failures to leave the financial result unchanged, so that a merchant outage cannot turn notification retries into new payments.
55. As an operator, I want expired work claims safely reclaimed and stale completions rejected, so that crashes and overlapping worker processes do not corrupt current state.
56. As an operator, I want actionably redacted diagnostics without credentials, card data, or checkout capabilities, so that I can investigate failures without exposing sensitive inputs.
57. As a maintainer, I want public routes to reject real card payloads and use only controlled synthetic references, so that the proof of concept cannot accidentally collect live card data.
58. As a maintainer, I want cached creation responses recognized as containing checkout credentials, so that exact response replay is not confused with storing only token hashes.
59. As a merchant application developer, I want generated OpenAPI to describe the actual validation, acknowledgments, errors, and financial-state behavior, so that integration does not depend on undocumented assumptions.
60. As a maintainer, I want the selected stack's database and validation capabilities checked before payment logic relies on them, so that incompatibilities are found at a small, understandable boundary.
61. As a maintainer, I want restart tests to terminate and relaunch real processes against durable local databases, so that the recovery claims are established by observable behavior.
62. As the project owner, I want concrete limitations reported before a fixed technology is replaced, so that implementation does not silently change the agreed stack.
63. As an operator, I want payment records, evidence, and command identities retained for the lifetime of prototype data, so that repeated demonstrations do not depend on destructive cleanup or expired identities.
64. As the project owner, I want a reproducible complete demonstration and an explicit account of unverified live-provider behavior, so that this prototype informs the later product without claiming production readiness.

## Implementation Decisions

1. Build three applications: Paybridge, the sample merchant application, and mock 4Cs. Each owns a separate durable local SQLite database. Runtime components communicate over HTTP and do not read another application's database. The test harness and trusted operator may inspect the mock ledger as synthetic reconciliation evidence.
2. Use TypeScript, Fastify, Prisma ORM 8, SQLite, ArkType, the Fastify Swagger plugin, Vitest, and Bun as package manager. Select a supported server runtime during the compatibility check. Bun as package manager does not itself choose the server runtime. Verify mutually compatible releases and retain a reproducible lockfile; report an essential limitation before substituting technology.
3. Keep payment rules and transactional commands in shared application services called by routes, workers, and trusted operator commands. Separate responsibilities for merchant configuration, idempotency, checkout, the 4Cs adapter, reconciliation, event history, webhook delivery, and work claims. Share protocol definitions across applications, not repositories or service-owned persistence.
4. Seed two merchant contexts with distinct synthetic provider accounts, Paybridge API credentials, webhook signing secrets, callback destinations, and permitted return origins. Bind provider-account configuration server-side. The caller cannot override it. Preserve that account identity on each payment attempt; its assignment remains fixed for the lifetime of prototype records. No signup or key-management workflow is added.
5. Define a merchant as the person or organisation collecting payments, separately from its integrating application. The merchant application owns business order-to-intent identity. It persists and reuses the binding and its command keys. Paybridge guarantees no duplicate successful collection within one intent; merchant references are not uniqueness constraints across intents, including within the same merchant.
6. Payment creation fixes the amount, currency, merchant reference, provider invoice, description input, and return destination as defined by the agreed contract. Validate a positive safe integer amount in minor units, supported currency metadata, bounded fields, and a return URL on the merchant's configured origin. Localhost HTTP is permitted for fixtures. Do not add an update-payment operation.
7. Preserve the payment states PENDING, PROCESSING, SUCCEEDED, FAILED, UNKNOWN, and CANCELLED. Only PENDING and definite FAILED permit a new attempt. At most one PROCESSING or UNKNOWN attempt exists per intent. SUCCEEDED and CANCELLED are terminal. UNKNOWN remains unresolved until recorded manual reconciliation establishes the outcome.
8. Treat definite AuthAndPost approval as the prototype success threshold of authorization and posting, not completed settlement. A provider financial decline and the selected definitive incomplete fixture produce FAILED while retaining their distinct provider codes. Interpret the outer operation, service result, and financial result in order; an HTTP success or arbitrary financial field attached to an invalid service result cannot establish approval.
9. Start each intent at revision one and increment the revision atomically for each committed status change. Public snapshots and financial events carry the revision. Observation-only history does not change state, advance a revision, or generate a financial webhook.
10. Scope command keys to the authenticated merchant. Require them for creation and both merchant and checkout confirmation. Hash the normalized validated command, operation, method, target, synthetic payment reference when applicable, and expected payment revision. Changed input or target under an existing key conflicts. Retain keys for the lifetime of prototype payment data without expiry or reuse.
11. An identical completed command returns its exact cached acknowledgment before current-state guards. For a new confirmation, require expectedRevision to equal the stored revision, then guard confirmable state and the absence of an unresolved attempt in the same transaction that creates the attempt, durable provider work, history, state revision, and acknowledgment. Invalid revision input is a bad request; an outdated revision is a payment_revision_conflict with no financial work created.
12. Payment creation returns a created response with the payment snapshot and checkout URL. Merchant confirmation returns accepted processing linked to the exact attempt. Checkout confirmation returns a See Other redirect after durable acceptance. Neither acknowledgment proves financial completion. Lookup returns current persisted Paybridge state, including PROCESSING or UNKNOWN, and does not query 4Cs.
13. After a stale-revision conflict, the sample refreshes its view and requires a deliberate new confirmation using the current revision and a new command key. It does not automatically refresh and resubmit the stale instruction. A true replay retains its old input and key. A new financial attempt after definite failure receives a new provider transaction identifier.
14. Only the authenticated merchant may permanently cancel a PENDING intent. Repeated cancellation of the same cancelled intent is a no-op without another financial event. Leaving checkout is navigation only in every payment state. It cannot stop an in-flight provider operation, change status, create an attempt, or emit a financial webhook. The sample retains an explicitly cancelled intent and its order binding and does not implement a replacement intent for that same order.
15. A payment identifier alone does not authorize checkout. Use a random payment-bound checkout capability, retain its authorization hash, and exclude capabilities from logs and diagnostics. Exact creation replay also retains the usable token in the cached response; treat those cached bytes as sensitive local records. This prototype adds neither production secret infrastructure nor a token-expiry subsystem.
16. The 4Cs adapter implements the documented SOAP operation's selected mock subset using AuthAndPost, the bound merchant's synthetic provider credential, a stable alphanumeric transaction identifier of at most sixteen characters, and a separately generated stable provider invoice reference. Generate collision-checked provider identifiers rather than truncating arbitrary merchant references. Convert money using integer-based formatting and explicit fixture currency metadata. Resolve card fields only from controlled synthetic references inside the adapter.
17. Record mock transaction identity and its final synthetic outcome atomically before deliberately losing or delaying a response. Outcomes are immutable. Every submission path honors the same account-and-transaction identity after concurrent execution or restart. A duplicate returns the provider-style duplicate result, not an invented replay of the earlier financial response. Paybridge continues generating globally unique provider transaction identifiers.
18. The mock's durable deduplication scope and finality are explicit simulation assumptions. The supplied provider guide does not establish live identity-retention duration, concurrent behavior, or failover durability. A synthetic payment-method reference is not evidence of live tokenization. The provider's repeat operation creates another transaction and is not used as lookup or recovery.
19. Commit a command, attempt, safe synthetic input, and provider work before any provider call. A reclaimed PROCESSING item reuses the same attempt and provider identity. A definitive response resolves it; ambiguity or a duplicate result commits UNKNOWN, completes financial submission work, and creates one reconciliation case. Do not continually submit a committed UNKNOWN attempt or generate a fresh identifier after a timeout.
20. Distinguish a request delayed before provider acceptance from a response delayed after a stored outcome. Local claim ownership protects Paybridge's writes, not an already sent request's remote effect. A missing mock ledger row, one pre-acceptance rejection, a timeout, or a lease expiry cannot establish final non-payment when another same-ID submission could still execute.
21. Retain the existing manual reconciliation workflow with REQUIRED, IN_PROGRESS, and RESOLVED cases, one per unknown attempt. Trusted local commands list, start, and resolve investigations. The operator checks the outcome, which may be success or definite non-payment. Match evidence to the provider account, transaction identifier, invoice, amount, and currency; retain the evidence reference, sanitized facts, operator identity, time, reason, and outcome.
22. A final stored mock approval supports successful resolution. A final stored decline or the chosen definitive incomplete fixture supports failed resolution only because every delayed same-ID submission must honor that immutable outcome. Missing, mismatched, or inconclusive evidence leaves the case open and another attempt blocked. Free-form notes alone do not establish an outcome. Do not add a mock closure operation or claim every unknown case eventually resolves.
23. Reconciliation atomically updates attempt and intent, advances revision, resolves the case, appends history, and creates the appropriate webhook. Repeating an identical resolution is a no-op; an incompatible second resolution is rejected. No worker automatically resolves a committed UNKNOWN attempt from a late reply.
24. Preserve bounded sanitized late provider observations in append-only history even when current ownership or financial-state guards reject their application. Keep the observation tied to the exact attempt and provider identity. Conflicting evidence on an already resolved attempt produces an actionable diagnostic and remains available for investigation; rewriting resolved financial decisions is outside this prototype.
25. Use durable provider and webhook outboxes and a durable merchant inbox. Claim work atomically with a fresh ownership token and an expiring lease, commit before external work, and guard completion by ownership and current state. Reclaim expired work after crashes. Keep loops local and HTTP calls bounded, outside database transactions. Webhook and recoverable inbox retries use capped backoff without changing event identity or starting another payment.
26. Store one webhook destination and signing secret per merchant. Sign the timestamp and exact stored payload bytes with HMAC-SHA256. A delivery retry preserves event ID and body but uses a current timestamp and signature. The receiver checks signature length, compares safely, verifies a configurable timestamp window in both directions, validates schema and event identity, and uses the secret associated with the configured destination rather than one selected from an untrusted payload.
27. Store the authenticated receiving merchant context with each durable inbox receipt before acknowledging it. An identical duplicate produces no second work item; conflicting bytes or receiving context under one event identity require investigation. Unknown local bindings remain pending. Before processing, require the receipt, payment binding, and order to have matching ownership, amount, currency, and business reference.
28. The sample application supports both merchant fixtures within its own database. Orders, payment bindings, prepared commands, and inbox receipts retain merchant context. Scope business-reference and command-key uniqueness to the merchant. Return lookup and command recovery use that merchant's server-side credential. A return-route payment ID must match the known local binding and never directly marks an order paid.
29. Apply webhook and lookup snapshots through the same guarded merchant operation. In one transaction, accept only a newer revision, apply the local order-paid effect once when appropriate, and complete inbox processing when applicable. Older or equal snapshots do not regress state. Do not wait for contiguous revisions because creation and processing do not have webhook types. The local paid effect is a database update; external fulfillment is excluded.
30. Persistence includes merchant configuration, intents, attempts, command identities and cached acknowledgments, append-only payment events, reconciliations and evidence, provider and webhook work, sample orders and payment views, prepared merchant commands, inbox receipts, and the mock ledger. Enforce ownership relationships, positive amounts, valid state, attempt numbering, one unresolved attempt per intent, durable event identity, and appropriate uniqueness through database constraints and transactional guards.
31. Retain payment history, command keys, evidence, and related records for the lifetime of prototype data. Preserve immutable financial inputs and historical bindings. No automatic purge, destructive reset of existing data, production database target, or production retention policy is part of this work.
32. Use ArkType for strict boundary validation and generate OpenAPI from the actual Fastify route schemas through the Swagger plugin. Reject unsupported fields rather than relying on silent removal. Preserve runtime restrictions that cannot be represented in JSON Schema and document them explicitly. Return stable JSON errors without stack traces or raw provider payloads. Financial decline and uncertainty are payment states, not generic HTTP server errors.
33. Keep Paybridge API credentials hashed, while distinguishing the retrievable synthetic provider credentials and webhook signing secrets needed by server operations. Reject real card payloads at public routes. Use parameterized database operations, safe XML serialization, bounded bodies, and an XML parser that disables external entities and DTD processing. Keep descriptions inert, redirect destinations constrained, sensitive responses uncached, diagnostics redacted, and demo servers local to the mock environment.
34. Complete the implementation in independently verifiable stages: stack and persistence compatibility; merchant boundary and payment commands; durable mock and provider recovery; manual reconciliation and evidence; merchant consumption and headless checkout; then the complete restart and failure demonstrations. Do not introduce a broker, worker framework, additional provider, or portability abstraction to support these stages.

## Testing Decisions

1. Use one primary behavioral test boundary: the complete journey through the applications' public HTTP interfaces, supplemented by the existing trusted operator-command interface for reconciliation. Launch the real local applications and workers with isolated synthetic databases. Drive merchant creation, checkout or direct confirmation, provider outcomes, callback receipt, lookup, and the merchant's local paid effect through that boundary. The owner approved these testing boundaries with the plan; this publication introduces no new business-facing test seam.
2. Follow the repository's Test Behavior, Not Implementation principle. A good test begins with an actual input or failure, exercises the real operation, and checks an observable acknowledgment, financial state, event, persisted evidence, or merchant effect. Expected results must be independent of the implementation under test. Mock call counts, generated constants, or assertions that objects merely exist do not prove the contract.
3. No application test prior art exists in the repository. Establish the shared integration setup once and reuse it. The supplied protocol examples, accepted state model, reference failure matrix, glossary, and ADRs are the starting expectations. The durable mock 4Cs service is an intentional dependency simulation, not a substitute for exercising Paybridge and merchant persistence.
4. Before the journey is built, use focused compatibility checks for the selected Prisma 8 SQLite extension and the validation/OpenAPI integration. Prove file persistence, rollback across the operations the design needs, parameter binding, affected-row reporting, foreign keys, check and partial unique constraints, competing process claims, contention handling, and restart durability. These checks use the real selected driver and database, not an in-memory repository replacement.
5. Verify creation replay, changed-input conflicts, immutable financial input, current-state lookup, merchant ownership, and inactive credentials. Exercise the same business reference under both fixture merchants and confirm their local order records remain separate. Demonstrate that wrong merchant credentials, payment IDs, callback contexts, or provider-account substitutions cannot cross ownership boundaries.
6. Test both confirmation entry points against the same payment behavior. Submit two different keys based on one revision, commit a decline before the delayed request arrives, and verify the delayed request is rejected without another attempt. Replay the original accepted command after the decline and verify its original acknowledgment. Then issue a deliberate new command based on the failed revision and establish that a new attempt is allowed.
7. Verify pending-only merchant cancellation, harmless repeat cancellation, and retained cancelled history and order binding. Exercise leaving checkout in every state and show that only navigation occurs. Demonstrate that a payer can resume an otherwise payable intent, while the sample cannot replace an explicitly cancelled intent for the same order.
8. Exercise layered provider interpretation with approval, decline, incomplete, invalid service results, malformed responses, and mismatched echoed fields. Verify exact amount formatting, valid stable references, account routing, and the distinction between service success and financial approval. Use synthetic or redacted data throughout.
9. Terminate and restart real processes around command commit, lost acknowledgment, provider acceptance, result persistence, webhook receipt, and inbox application. Reopen the same local database files and verify that command identity, provider transaction identity, work, evidence, and merchant effects survive. Reinstantiating objects in one process does not establish the restart guarantee.
10. Use the mock ledger as independent evidence of simulated financial effects. Prove that duplicate and delayed same-ID submissions honor an immutable recorded outcome across provider restart. Distinguish identity reuse from proof of successful payment and verify that ambiguous duplicate recovery creates one unknown case.
11. Hold a provider request before acceptance, time it out, and demonstrate that missing ledger evidence cannot resolve failure or permit another attempt. Release it and investigate its actual outcome. Separately, store a decline, lose the response, reconcile from that final evidence, and issue a deliberate fresh attempt; a delayed old submission must still honor its earlier decline.
12. Exercise manual reconciliation to both success and failure using matching evidence. Reject mismatched or inconclusive evidence. Verify operator and evidence history, revision advancement, state changes, and webhook creation as one committed result. Verify harmless repeated resolution, rejected conflicting resolution, and retained UNKNOWN when no outcome can be established.
13. Exercise overlapping claims and stale worker completion. Verify that a stale worker cannot overwrite a current or resolved result, while a sanitized late observation remains available. Inspect persisted history and externally visible state rather than checking only internal claim-helper calls.
14. Verify raw-byte signatures, timestamp limits, event identity, malformed webhook rejection, and configured receiving merchant context. Crash before and after receipt acknowledgment and prove the correct redelivery or recovery behavior. A webhook authenticated for one merchant must never apply another merchant's payment or paid effect.
15. Deliver duplicate, delayed, reordered, and revision-gapped notifications. Race lookup against webhook processing. Verify one durable receipt per event, a single local paid effect, no state regression, and retention of receipts awaiting local binding. Simulate a merchant outage and establish that payment state stays fixed while notification work survives and later resumes.
16. Verify safe return destinations, ownership-scoped return lookup, capability requirements, strict request validation, rejection of real card fields, inert descriptions, safe XML construction, and redaction of sensitive cached acknowledgments and headers. Confirm that both a valid operation and an invalid alternative behave as intended; absence-only assertions are insufficient.
17. Validate the generated OpenAPI against actual route requests, responses, headers, and errors. Demonstrate unrepresentable validation restrictions explicitly. Run the final HTTP demonstrations and failure suite against the same implementation that is documented, and record any remaining unverified guarantees.

## Out of Scope

- Customer release, production deployment, live NCBA/4Cs connectivity, bank certification, and real card collection.
- Payer checkout UI, merchant portal, dashboards, treasury screens, administration UI, and interactive documentation UI.
- Self-service merchant signup, real provider-key submission, credential rotation, multiple provider accounts per fixture merchant, and multiple webhook endpoints per merchant.
- Refunds, partial capture, separate authorization and capture, subscriptions, repeat charging, saved real payment methods, and additional providers.
- Replacement intents for the same sample order after explicit merchant cancellation, reopening a cancelled intent, and rewriting resolved financial decisions.
- Automatic financial retry of a committed unknown outcome, an invented provider status-lookup or tokenization API, a mock closure mechanism, and a promise that every unknown case eventually resolves.
- Production PCI certification, production secret infrastructure, automatic token-expiry workflows, final production retention policy, and destructive cleanup of existing records.
- A message broker, hosted queue, distributed worker platform, worker framework, and final process-supervision or deployment architecture.
- External order fulfillment or customer notifications beyond the sample's guarded local paid effect and Paybridge webhook flow.
- Predecessor API compatibility, ASP.NET portability, a Go implementation, and abstractions introduced solely for a possible later port.
- Claims of exactly-once distributed delivery, settlement finality, or compatibility certification with the current live provider.
