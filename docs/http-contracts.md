# HTTP contracts and observed behavior

Each application serves OpenAPI 3.1 generated by `@fastify/swagger` from its registered Fastify route schemas. With the default local ports running:

```sh
curl --fail http://127.0.0.1:3100/openapi.json
curl --fail http://127.0.0.1:3101/openapi.json
curl --fail http://127.0.0.1:3102/openapi.json
```

The document endpoint includes its own JSON response contract. It is public infrastructure, has no credentials or checkout capabilities in its generated content, and returns `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. There is no interactive documentation UI. Only explicit methods are registered. Automatic HEAD routes are disabled, so HEAD receives 404 rather than invoking a hidden GET operation.

There are 20 explicit operations across the three applications, including their document endpoints. The tables below name observed responses compared with each operation's own generated body and header schemas. Common error maps declare additional statuses that are not reachable from every operation. A declaration alone is not evidence that a branch executed.

## Paybridge

All business responses use `no-store` and `nosniff`. Unmatched JSON routes return `404 route_not_found` with the common error envelope and a request ID; their response never echoes the request URL or capability query. JSON uses `application/json; charset=utf-8`. Creation and confirmation acknowledgments include `Location`. Checkout redirects have status 303, an empty `text/plain; charset=utf-8` body and the registered return destination. A cached acknowledgment retains its original status, bytes and headers, while lookup reports current payment state.

Actual 503 responses are checked against `Retry-After: 1`. Tests do not insert an artificial stranded command merely to claim that branch is reachable. They establish concurrent acceptance, bounded 503 contention and exact replay instead.

The 502 scenario points the merchant at the real local SOAP mock instead of Paybridge. Its incompatible HTTP error envelope is rejected without replacing the merchant's existing binding or prepared command. This proves that response-validation branch, not every possible malformed upstream response. The outage checks stop an owned upstream process and observe retained work plus 503 through the public merchant routes.

Receipt 204 means an authenticated inbox record committed. Its body is absent, not JSON `null`, and it does not establish that the order has been paid. [Webhook delivery](webhook-delivery.md) and [inbox processing](merchant-inbox.md) describe the separate receipt and application transactions.

## Synthetic SOAP mock

POST `/TranSvcs/ssis.asmx` consumes `text/xml` and requires this exact quoted header value:

```http
SOAPAction: "http://equament.com/Schemas/Fmx/ssis/SSISProcessTransaction"
```

The generated contract describes a string carrying SOAP XML. `tests/mock-fourcs/openapi.test.ts` compares actual requests and responses with that contract for 200, 400, 413, 415 and 500. Successful replies use `text/xml; charset=utf-8`; protocol error replies use `text/xml`. Both contain UTF-8 XML strings. There is no JSON error envelope for this operation.

HTTP 200 may carry `SecurityError`, `DuplicateTransaction`, or a financial decline. Interpret outer operation, service and financial results separately. The intentional malformed fixture returns `<invalid` with 200 after recording its synthetic outcome. A lost-response fixture disconnects without an HTTP status; it is not represented as a fictitious success acknowledgment in OpenAPI. Resubmitting its same account and transaction identity returns the documented duplicate result and preserves one ledger effect. An injected test-only failure after acceptance produces the XML 500 response and likewise preserves the accepted outcome. The normal entrypoint has no HTTP fault endpoint.

GET `/openapi.json` is the mock's second operation and follows the common document contract. The mock has no HTTP transaction lookup or repeat-operation endpoint. Trusted local ledger inspection remains separate. These schemas do not claim compatibility with the current live provider.

## Restrictions beyond JSON Schema

- Runtime text limits count UTF-16 code units; JSON Schema lengths count Unicode code points. Existing payment and stack tests demonstrate the difference with valid and overlong emoji controls. Stored-text restrictions also reject NUL and unpaired surrogates.
- Return destinations must match the authenticated merchant's configured origin and permitted URL form. Activity, ownership, canonical command identity, current revision, unresolved attempts and binding consistency depend on persisted facts. A scalar schema cannot authorize them.
- Checkout capability authorization deliberately returns generic 404 for missing, malformed and mismatched tokens. The token is represented by the OpenAPI query security scheme, rather than a second ordinary query parameter. Unknown query keys still fail validation. A redirect or return query never supplies financial evidence.
- Bodyless commands reject supplied bodies explicitly. Absence of `requestBody` in OpenAPI alone does not prohibit incoming bytes. Strict empty query objects are emitted with `properties: {}` so Swagger does not mistake JSON Schema keywords for query parameter names.
- Webhooks authenticate exact UTF-8 bytes with the destination's secret before JSON parsing. HMAC, timestamp tolerance in both directions, calendar validity, header/payload identity, immutable duplicate bytes and durable receipt are runtime requirements. The 16,384-byte limit is independent of string length. JSON with a quoted or mixed-case UTF-8 charset remains valid; other encodings are rejected.
- SOAP requires exact hierarchy and namespaces, one expected child per field, XML 1.0, bounded structure and only synthetic fixture fields. DTDs and custom/external entities are rejected; predefined XML escapes are supported. Its amount and identifier rules, configured provider account and immutable duplicate outcome are checked by the parser and database. An XML string schema does not prove those properties. The retained mock HTTP tests exercise valid controls and rejected alternatives.

## Verification

Run the complete retained checks with `bun run test` and typecheck with `bun run typecheck`. The new contract comparisons can be run with:

```sh
bun run test tests/contracts tests/mock-fourcs/openapi.test.ts
```

The shared helper compiles schemas fetched from each running application's document and checks actual response bodies, media types and required headers. Parameter checks use actual IDs and command headers. Existing rollback and contention tests now compare their real error replies as well as their durable effects. Those tests retain their original transport, lease and contention bounds.

The router regression first failed on missing `Cache-Control` for a malformed payment path. After the shared header correction, it exposed the missing webhook 414 declaration. The HEAD regression first observed an undocumented 200. The document comparison also exposed the two invented query parameters. Each correction has a retained real-HTTP regression with valid controls. The Fix Root Causes principle led to correcting the shared router response and empty-object schema translation instead of patching individual routes.

No database migration, record reset, financial state change, live-provider call or production fault endpoint is part of this contract work. The final combined suite and demonstration results belong in the complete prototype verification trace.
